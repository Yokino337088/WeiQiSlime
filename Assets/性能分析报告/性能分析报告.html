通过 在接近满盘（60/81 棋子）的战斗压力下，游戏稳定跑在帧率上限，主线程仅用掉约四分之一预算， 渲染线程 ~3ms、GPU 1–2ms。先前"棋子一多就掉帧"的问题没有复现。

注意 编辑器失焦时游戏会被节流（帧间隔飙到 ~100ms，但主线程只有 6.5ms）—— 这是 PlayerSettings 里 runInBackground: 0 导致的编辑器行为，不是游戏性能问题； 测性能时必须让 Unity 窗口保持前台（或勾选 Run In Background），否则数据完全不可用。

六、关键发现

  1. 满盘压力下帧率有余量。60 个棋子（9×9 棋盘）时主线程 4.2–4.8ms， 远低于 16.7ms 预算；SpriteRenderer.PrepareNode 仅 0.46ms， 说明棋子渲染与逻辑都不再随数量线性恶化。
  2. 编辑器失焦会节流（重要干扰项）。runInBackground: 0 时编辑器失焦 → 帧间隔 100ms、 但主线程只有 6.5ms，说明是"没在跑"而不是"跑不动"。后续所有性能对比都必须在 Unity 前台的条件下做， 或先把 Run In Background 勾上。
  3. UI（UGUI Canvas）是渲染侧最大单项。采样瞬间 Canvas.Sort 1.89ms、 Canvas.GeometryJob 1.42ms、Canvas.PrepareBatches 0.60ms， 而 UIR.DrawChain 出现 18.68ms 的采样值（可能含多帧累计，仅供参考）。 UI 的合批/重建成本已经高于棋子本身。
  4. 每帧仍有 12–31KB 托管分配。会产生周期性 GC（尖峰而非均值问题）。 旧的"每棋子协程 + 每帧 new List"已消失（协程计数器 CoroutinesDelayedCalls 读数 0）， 剩余分配源需要开 Allocation Callstacks 定位。
  5. 战斗在采样期间处于静止。棋子数 60 恒定、AI 未继续落子，因此拿到的是"高负载静态盘面"， 而不是"持续落子 + 攻击特效齐发"的峰值场景；峰值需要用脚本压测或人工连续落子来补测。

七、优化建议（按收益排序）

  1. 拆 Canvas：把每帧变化的元素（金币/行动力/血条/倒计时）从主 Canvas 拆到独立 Canvas，减少整块 Canvas 的重建与排序；静态 UI 保持同图集同材质。
  2. 消 GC 分配：用 Profiler 的 Allocation Callstacks（profiler_start(enable_callstacks=true)）抓一次落子/攻击过程的分配栈，优先清掉每帧都发生的分配（字符串拼接、装箱、闭包、LINQ）。
  3. 补峰值压测：满盘 + 连续落子 + 多枚子弹同时命中时再采一轮（可用调试菜单加"批量落子"键实现），确认峰值下主线程仍 <8ms。
  4. 真机复测：Android 上关闭 ABResMgr.isDebug 走 AB 流程，重点看加载期卡顿与图集显存（2048×2048）表现；编辑器数据不能代表手机。
  5. 可选：被围标识（围_0001）目前只有被围的棋子才推进帧动画，已是最优；若要进一步省，可把它的帧率降到 10fps。
